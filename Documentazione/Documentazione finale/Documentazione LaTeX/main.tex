\subsection{Caratterizzazione Target Utenti}
Il sistema BugBoard26 è progettato per servire diverse tipologie di utenti,
ciascuna con competenze, esigenze e modalità d'uso specifiche.

\subsubsection*{1. Sviluppatori e QA Tester (Utenti Operativi)}
\begin{itemize}
    \item \textbf{Esperienza Informatica:} Elevata; sono abituati a IDE, terminali e sistemi di versioning.
    \item \textbf{Conoscenza del Dominio:} Media/Alta; comprendono perfettamente il ciclo di vita di un bug (TODO $\to$ Resolved).
    \item \textbf{Frequenza d'uso:} Alta (uso quotidiano).
    \item \textbf{Necessità:} Velocità nell'inserimento delle issue e possibilità di allegare prove tecniche come screenshot.
\end{itemize}

\subsubsection*{2. Team Leader e Admin (Utenti Gestionali)}
\begin{itemize}
    \item \textbf{Esperienza Informatica:} Elevata.
    \item \textbf{Conoscenza del Dominio:} Massima; hanno la visione globale del progetto e delle priorità.
    \item \textbf{Frequenza d'uso:} Alta.
    \item \textbf{Necessità:} Strumenti di supervisione (Dashboard) e gestione dei permessi (rimozione duplicati, archiviazione, ecc\dots).
\end{itemize}

\subsubsection*{3. Stakeholder e Clienti (Utenti Osservatori)}
\begin{itemize}
    \item \textbf{Esperienza Informatica:} Variabile (spesso Bassa/Media).
    \item \textbf{Conoscenza del Dominio:} Bassa/Media; interessati ai progressi macroscopici.
    \item \textbf{Frequenza d'uso:} Bassa (settimanale o mensile).
    \item \textbf{Necessità:} Una modalità "readonly" semplice che non permetta modifiche accidentali e offra report chiari.
\end{itemize}

\subsection{Requisiti Non-Funzionali e di Sistema}
Questi requisiti definiscono le qualità del sistema e i vincoli tecnologici.
Seguendo la traccia del progetto e le buone norme dell'Ingegneria del Software,
possiamo categorizzarli come segue.

\subsubsection*{Requisiti di Sistema (Vincoli della Traccia)}
\begin{itemize}
    \item \textbf{RNF\_01 - Architettura}: Il sistema deve essere distribuito, con Back-end e Front-end logicamente e fisicamente indipendenti.
    \item \textbf{RNF\_02 - Tecnologia}: Entrambi i componenti devono essere realizzati con linguaggi di programmazione Object-Oriented.
    \item \textbf{RNF\_03 - Comunicazione}: Il Front-end deve comunicare con il Back-end esclusivamente tramite API (es. REST) via rete.
    \item \textbf{RNF\_04 - Deployment}: Il Back-end deve essere predisposto per l'esecuzione tramite container Docker.
\end{itemize}

\subsubsection*{Requisiti di Qualità (Proprietà Emergenti)}
\begin{itemize}
    \item \textbf{Sicurezza (Security):} Le password non devono essere salvate in chiaro nel database, ma tramite algoritmi di hashing sicuri (es. BCrypt). L'accesso alle API deve essere protetto da token di sessione (es. JWT) per garantire l'integrità dei dati.

    \item \textbf{Affidabilità e Robustezza (Reliability):} Il sistema deve gestire gli errori di rete tra client e server mostrando messaggi informativi e non interrompendo l'esecuzione (come previsto nei diagrammi di Cockburn).

    \item \textbf{Usabilità (Usability):} L'interfaccia deve essere intuitiva: un utente "Standard" deve essere in grado di creare una nuova issue in meno di 30 secondi dal primo accesso.
\end{itemize}

\section{Formalizzazione R16}

\subsection{processDuplicate}
Il metodo \texttt{processDuplicate} gestisce la marcatura di una issue come duplicato di un'altra. Il metodo esegue le seguenti azioni principali: verifica la legittimità dell'operatore (deve essere un Admin), valida gli identificativi passati, controlla l'esistenza delle issue coinvolte, e in caso di successo imposta lo stato della issue duplicata su CLOSED, registra la data di chiusura e mantiene il riferimento all'originale.

\subsection{createUser}
Il metodo \texttt{createUser} (esposto dall'\texttt{AdminController}) permette ad un amministratore di creare una nuova utenza: verifica i parametri in ingresso, controlla i permessi dell'operatore, assicura l'unicità dell'email, genera una password temporanea cifrata e provvede al salvataggio della nuova utenza nel repository.

\subsection{Strategie e Tecnologie di Testing (8.4.b)}

La suite di test è stata progettata seguendo un approccio di \textbf{White Box Testing}, focalizzato sulla copertura strutturale del codice sorgente e sulla verifica completa di tutti i rami decisionali.

\subsubsection{Framework e Strumenti Utilizzati}

\begin{itemize}
    \item \textbf{JUnit 4}: Framework di unit testing per Java utilizzato per la definizione e l'esecuzione dei test case. Fornisce le annotazioni \texttt{@Test}, \texttt{@Before}, \texttt{@After} e supporto per eccezioni attese tramite \texttt{expected=}.
    
    \item \textbf{Mockito}: Libreria di mocking per simulare il comportamento dei componenti di persistenza (repository) in modo isolato dalla logica di business. Consente di definire stub e spy per controllare i comportamenti dei mock.
    
    \item \textbf{Maven}: Build tool utilizzato per compilazione, esecuzione dei test e gestione delle dipendenze. I test vengono eseguiti durante la fase di build con il plugin Surefire.
    
    \item \textbf{JaCoCo (Java Code Coverage)}: Tool per misurare la copertura di codice durante l'esecuzione dei test. Genera report dettagliati (in formato HTML) indicando quali linee di codice e rami decisionali sono stati testati.
\end{itemize}

\subsubsection{Strategie di Progettazione dei Test}

\begin{itemize}
    \item \textbf{White Box Testing (Structural Testing)}: L'approccio adottato richiede la conoscenza approfondita del codice sorgente e mira a coprire tutti i percorsi di esecuzione possibili. Ogni test case è progettato per esercitare almeno un nuovo ramo (branch) del codice.
    
    \item \textbf{Branch Coverage}: Tutti i test case sono stati definiti per garantire che ogni ramo decisionale (\textit{branch}) delle istruzioni condizionali (if, else, switch) venga eseguito almeno una volta. Ad esempio, nei test di \texttt{processDuplicate}, i TC2-TC4 coprono il ramo relativo ai controlli di sicurezza, mentre i TC5-TC11 coprono le validazioni degli input e l'integrità del dominio.
    
    \item \textbf{Equivalence Partitioning}: Per minimizzare la ridondanza, gli input sono stati suddivisi in classi di equivalenza valide e non valide. Ad esempio:
        \begin{itemize}
            \item Valide: Admin autenticato, ID esistenti, email/username univoci e ben formattati.
            \item Non valide: User semplice, ID null o non trovati, email/username duplicate, parametri vuoti.
        \end{itemize}
    
    \item \textbf{Boundary Value Analysis}: Sono stati identificati e testati casi limite che generalmente contengono difetti. Ad esempio, il test TC9 di \texttt{processDuplicate} verifica il caso limite in cui un issue viene marcato come duplicato di se stesso; i test TC7, TC8 e TC11 coprono le verifiche di esistenza delle risorse (uno mancante, l'altro mancante, entrambi mancanti).
    
    \item \textbf{State-Based Testing}: Per metodi che modificano lo stato delle entità (come \texttt{processDuplicate} e \texttt{finalizeProfile}), i test verificano che gli aggiornamenti dello stato siano corretti attraverso asserzioni e verifiche tramite \texttt{verify()}.
\end{itemize}

\subsubsection{Tecniche di Isolamento e Mocking}

\begin{itemize}
    \item \textbf{Mockito.mock()}: Crea mock objects completamente controllati per simulare il comportamento dei repository senza accedere al database reale.
    
    \item \textbf{Mockito.spy()}: Avvolge oggetti reali (ad es. istanze di \texttt{User}, \texttt{Issue}) permettendo di monitorarne il comportamento senza interferire con la logica interna. Utile per verificare i side effects (cambiamenti di stato) sugli oggetti durante i test.
    
    \item \textbf{when().thenReturn()}: Configura il comportamento atteso dei mock per input specifici, permettendo di testare diversi scenari (successo, eccezioni, etc.) senza dipendenze dal database.
    
    \item \textbf{verify()}: Verifica che i mock siano stati chiamati con i parametri attesi, assicurando che le operazioni di persistenza avvengano solo nei casi appropriati. Ad esempio, \texttt{verify(userRepository, never()).save(any(User.class))} assicura che nessun salvataggio avvenga in caso di errore.
    
    \item \textbf{Optional.of() / Optional.empty()}: Simulano i comportamenti del repository nel ritornare entità trovate o non trovate, mantenendo coerenza con le firme dei metodi reali che ritornano \texttt{Optional<T>}.
\end{itemize}

\subsubsection{Copertura e Validazione}

La suite di test raggiunge una copertura di codice elevata per i tre metodi critici testati:

\begin{itemize}
    \item \textbf{processDuplicate}: 11 test case coprono tutti i rami decisionali (controlli di sicurezza, validazione input, verifiche di esistenza, gestione degli stati).
    \item \textbf{createUser}: 9 test case coprono l'autenticazione, la validazione degli input, i permessi amministrativi e il vincolo di unicità dell'email.
    \item \textbf{finalizeProfile}: 6 test case coprono la validazione dei parametri, il controllo di unicità dello username e l'aggiornamento dello stato.
\end{itemize}

I test sono configurati per essere eseguiti automaticamente durante la build Maven (fase \texttt{test}) e i report di copertura JaCoCo sono generati in \texttt{target/site/jacoco/index.html}, fornendo una visione dettagliata della completezza della suite di test.
