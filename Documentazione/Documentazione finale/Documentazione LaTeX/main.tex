\subsection{Caratterizzazione Target Utenti}
Il sistema BugBoard26 è progettato per servire diverse tipologie di utenti,
ciascuna con competenze, esigenze e modalità d'uso specifiche.

\subsubsection*{1. Sviluppatori e QA Tester (Utenti Operativi)}
\begin{itemize}
    \item \textbf{Esperienza Informatica:} Elevata; sono abituati a IDE, terminali e sistemi di versioning.
    \item \textbf{Conoscenza del Dominio:} Media/Alta; comprendono perfettamente il ciclo di vita di un bug (TODO $\to$ Resolved).
    \item \textbf{Frequenza d'uso:} Alta (uso quotidiano).
    \item \textbf{Necessità:} Velocità nell'inserimento delle issue e possibilità di allegare prove tecniche come screenshot.
\end{itemize}

\subsubsection*{2. Team Leader e Admin (Utenti Gestionali)}
\begin{itemize}
    \item \textbf{Esperienza Informatica:} Elevata.
    \item \textbf{Conoscenza del Dominio:} Massima; hanno la visione globale del progetto e delle priorità.
    \item \textbf{Frequenza d'uso:} Alta.
    \item \textbf{Necessità:} Strumenti di supervisione (Dashboard) e gestione dei permessi (rimozione duplicati, archiviazione, ecc\dots).
\end{itemize}

\subsubsection*{3. Stakeholder e Clienti (Utenti Osservatori)}
\begin{itemize}
    \item \textbf{Esperienza Informatica:} Variabile (spesso Bassa/Media).
    \item \textbf{Conoscenza del Dominio:} Bassa/Media; interessati ai progressi macroscopici.
    \item \textbf{Frequenza d'uso:} Bassa (settimanale o mensile).
    \item \textbf{Necessità:} Una modalità "readonly" semplice che non permetta modifiche accidentali e offra report chiari.
\end{itemize}

\subsection{Requisiti Non-Funzionali e di Sistema}
Questi requisiti definiscono le qualità del sistema e i vincoli tecnologici.
Seguendo la traccia del progetto e le buone norme dell'Ingegneria del Software,
possiamo categorizzarli come segue.

\subsubsection*{Requisiti di Sistema (Vincoli della Traccia)}
\begin{itemize}
    \item \textbf{RNF\_01 - Architettura}: Il sistema deve essere distribuito, con Back-end e Front-end logicamente e fisicamente indipendenti.
    \item \textbf{RNF\_02 - Tecnologia}: Entrambi i componenti devono essere realizzati con linguaggi di programmazione Object-Oriented.
    \item \textbf{RNF\_03 - Comunicazione}: Il Front-end deve comunicare con il Back-end esclusivamente tramite API (es. REST) via rete.
    \item \textbf{RNF\_04 - Deployment}: Il Back-end deve essere predisposto per l'esecuzione tramite container Docker.
\end{itemize}

\subsubsection*{Requisiti di Qualità (Proprietà Emergenti)}
\begin{itemize}
    \item \textbf{Sicurezza (Security):} Le password non devono essere salvate in chiaro nel database, ma tramite algoritmi di hashing sicuri (es. BCrypt). L'accesso alle API deve essere protetto da token di sessione (es. JWT) per garantire l'integrità dei dati.

    \item \textbf{Affidabilità e Robustezza (Reliability):} Il sistema deve gestire gli errori di rete tra client e server mostrando messaggi informativi e non interrompendo l'esecuzione (come previsto nei diagrammi di Cockburn).

    \item \textbf{Usabilità (Usability):} L'interfaccia deve essere intuitiva: un utente "Standard" deve essere in grado di creare una nuova issue in meno di 30 secondi dal primo accesso.
\end{itemize}

\subsection{processDuplicate}
Il metodo \texttt{processDuplicate} gestisce la marcatura di una issue come duplicato di un'altra. Il metodo esegue le seguenti azioni principali: verifica la legittimità dell'operatore (deve essere un Admin), valida gli identificativi passati, controlla l'esistenza delle issue coinvolte, e in caso di successo imposta lo stato della issue duplicata su CLOSED, registra la data di chiusura e mantiene il riferimento all'originale.

\subsection{createUser}
Il metodo \texttt{createUser} (esposto dall'\texttt{AdminController}) permette ad un amministratore di creare una nuova utenza: verifica i parametri in ingresso, controlla i permessi dell'operatore, assicura l'unicità dell'email, genera una password temporanea cifrata e provvede al salvataggio della nuova utenza nel repository.

\subsubsection{Codice per test di unità automatici (8.4.b)}
I test di unità sono stati realizzati utilizzando il framework \textbf{JUnit 4} e la libreria di mocking \textbf{Mockito}. La classe di test \texttt{IssueServiceTest.java} implementa i 11 scenari descritti nel Test Plan, assicurando l'isolamento della logica di business dai componenti di persistenza. Il codice è strutturato per verificare sia il corretto aggiornamento dello stato delle entità (TC1) sia il sollevamento delle eccezioni appropriate in caso di violazione dei vincoli (TC2-TC11).

Il codice dei test è consultabile nel repository GitHub (\href{https://github.com/patt509/BugBoard26.git}{\texttt{\seqsplit{https://github.com/patt509/BugBoard26.git}}}) al seguente percorso: \texttt{\seqsplit{backend/src/test/java/com/bugboard/service/IssueServiceTest.java}.}

\subsubsection{Strategie di progettazione dei test (8.4.c)}
Per la progettazione della suite di test è stato adottato un approccio di \textbf{White Box Testing}, focalizzato sulla copertura strutturale del codice sorgente. Sono state coperte dai TC tutte le righe di codice e i rami decisionali della funzione \texttt{processDuplicate}.

\begin{itemize}
    \item \textbf{Criterio di copertura strutturale (Branch Coverage):} I test case sono stati definiti per garantire che ogni ramo decisionale (\textit{branch}) delle istruzioni condizionali presenti nel metodo \texttt{processDuplicate} venga eseguito almeno una volta. Ad esempio, i TC2-TC4 coprono il ramo relativo ai controlli di sicurezza, mentre i TC5-TC11 coprono le validazioni degli input e l'integrità del dominio, inclusi i casi di non esistenza (singolo issue o entrambi).
    \item \textbf{Analisi delle classi di equivalenza:} Sono state identificate partizioni di input valide (Admin autenticato, ID esistenti e distinti) e non valide (User semplice, ID null o coincidenti) per minimizzare la ridondanza dei test massimizzando la capacità di individuare bug.
    \item \textbf{Analisi dei valori limite:} Il test TC9 verifica specificamente il caso limite in cui l'ID della risorsa duplicata coincide con quello della risorsa originale, prevenendo stati inconsistenti nel sistema. I TC7, TC8 e TC11 coprono invece le verifiche di esistenza delle risorse nel repository (uno mancante, l'altro mancante, o entrambi mancanti).
    \item \textbf{Utilizzo di Mock e Spy:} La strategia ha previsto l'uso di \texttt{Mockito.spy()} per monitorare il comportamento delle istanze di \texttt{Issue} e \texttt{verify()} per accertarsi che il salvataggio sul repository avvenga solo nelle condizioni di successo previste.
\end{itemize}

\subsubsection{Codice per test di unità automatici (8.4.b)}

La classe di test \texttt{AuthServiceTest.java} implementa i 9 scenari descritti nel Test Plan, assicurando la corretta validazione degli input, il controllo dei permessi amministrativi e l'unicità delle email. \subsubsection{Strategie di progettazione dei test (8.4.c)}

Per la progettazione della suite di test è stato adottato un approccio di \textbf{White Box Testing}, focalizzato sulla copertura strutturale del codice sorgente. Sono state coperte dai TC tutte le righe di codice e i rami decisionali della funzione \texttt{createUser}.

\begin{itemize}
    \item \textbf{Criterio di copertura strutturale (Branch Coverage):} I test case sono stati definiti per garantire che ogni ramo decisionale delle istruzioni condizionali presenti nel metodo \texttt{createUser} venga eseguito almeno una volta. I TC3-TC4 verificano i controlli di autenticazione dell'amministratore (ID null o non trovato), i TC5-TC7 coprono la validazione degli input (email/role null/empty), il TC8 copre il controllo dei permessi amministrativi e il TC9 verifica il vincolo di unicità dell'email.
    \item \textbf{Analisi delle classi di equivalenza:} Sono state identificate partizioni di input valide (Admin autenticato, email valida e non presente nel sistema) e non valide (parametri null/empty, utente non admin, email duplicata) per minimizzare la ridondanza dei test massimizzando la capacità di individuare bug.
    \item \textbf{Testing degli effetti collaterali:} Per i casi di errore (TC3-TC9), oltre alla verifica del sollevamento dell'eccezione appropriata, è stato utilizzato \texttt{verify(userRepository, never()).save(any(User.class))} per garantire che nessuna operazione di persistenza venga eseguita in presenza di violazioni dei vincoli.
    \item \textbf{Utilizzo di Mock Objects:} La strategia ha previsto l'uso di \texttt{Mockito} per simulare il comportamento del \texttt{UserRepository}, permettendo di testare la logica di business in isolamento dal layer di persistenza. Il mock è configurato per restituire \texttt{true} o \texttt{false} dal metodo \texttt{existsByEmail()} a seconda dello scenario testato.
\end{itemize}
